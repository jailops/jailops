# What 1.0 promises

This page is for the person who decides to run JailOps on many hosts and for the one who decides when 1.0.0 is released. It says what
the version promises, what it does not, and the gates a release has to pass.

## The promise

From 1.0.0 these hold for every 1.x release:

| Promise | What it means | How it is checked |
|---|---|---|
| **The API surface is frozen** | Routes, members, statuses, error codes, the envelope of every answer, `ETag` and `If-Match`, the life of an asynchronous operation and the capability names do not change in a way that breaks a client. A break needs a new extension name and a major version. | The contract tests and `just freeze` ([api.md](api.md#what-is-frozen)); the client library of an earlier release runs against the current server on every change |
| **The extensions of the 1.x list keep their behaviour** | The list is in [api.md](api.md#which-extensions-carry-the-1x-promise). The extensions of the second list are real and tested, and a break in them is a release note and a new extension name | `TestFreezeEveryExtensionHasAPromise`: every extension is in exactly one list |
| **A host upgrades in place** | Each release upgrades from the previous one, and from any release from 0.8.0 on, without recreating a jail, a network or a volume. Stored state is converted by itself at the first start, forwards only, and a database or an object that is newer than the binary is refused | [upgrade-guarantee.md](upgrade-guarantee.md); a fixture of every release, `go test ./internal/upgradecheck`, and the nightly upgrade run on a host |
| **Command output for scripts is stable** | `-o json` and `-o yaml` of the commands in [api.md](api.md#what-is-frozen) keep their names and types; the exit status of an error code is fixed | The transcripts and golden files of `internal/cli`, `just freeze` |
| **The supported FreeBSD releases work** | The releases of [supported-versions.md](supported-versions.md), on the architectures of that page, with the PF traffic matrix and the clean-install run passed on each | The CI gate, the nightly runs, [release-engineering.md](release-engineering.md) |
| **Every object has one owner** | Authority is local: the host that stores an object is the truth, a `fleet` object is managed with one definition and is not shared state, and the table "Resource authority" in [design.md](design.md#71-authority) says who owns and who may write each kind | `api.Authorities` and the tests that keep it equal to the code and the document |
| **JailOps never edits `/etc/pf.conf`** | The host has one line, `anchor "jailops/*"`; the firewall of the jails is in the anchors and the host's own rules stay the host administrator's | [networking.md](networking.md), the PF tests |

## What is not promised

- **Cluster mode** is not planned ([roadmap.md](roadmap.md#not-planned)): JailOps provides the primitives, not the orchestration. Nothing in 1.0
  depends on it and nothing of it is built.
- **Moving a jail to another host as one command**, a copy kept on another host and promoted, `jailops jail monitor` and graphs.
  **Automatic failover is not planned.** `jail export` and `jail import` move a jail as a file today.
- **Shared address space across hosts.** Overlap is checked on one host; a prefix, an NDP proxy or a public address that two hosts
  share needs one owner that JailOps does not enforce ([networking.md](networking.md#networks-belong-to-a-host)).
- **The extensions of the second list** (backups, `fleet_projects`, `sealed_secrets` and the other names that api.md lists as "Not yet"):
  they are frozen like the rest, but a break in them is a release note and a new extension name, not a major version.
- **FreeBSD releases that the matrix does not list**, and a major release before its packages exist (`FreeBSD:16` needs its own build).
- **Wording of the command line and of the console** is not frozen: help texts, human output and labels may change in any release
  and the transcripts say when they did.

## Ready for 1.0

1.0.0 is released when every line of this list is true, one run on a host each, and not before.

| Gate | What has to be true | How it is verified |
|---|---|---|
| CI | Every job of the CI run on master is green, the eight FreeBSD VM jobs included (the Go tests, three end-to-end shards and four packet filter shards) | `gh run list` on master; the debug script when a job fails |
| Contract | `just freeze` changes nothing; the previous-client test passes with a baseline of the last release; the golden files of the routes, error codes, envelopes, enums, conditions, wire transcripts and the command tree are in place | `just freeze`, `go test ./internal/server -run PreviousSDK` |
| Compatibility gates | The gates that [compatibility.md](compatibility.md#what-the-tests-prove-and-what-they-do-not) lists as not built (the replays of command lines and of whole hub and host conversations) have the reason that page gives | The same page |
| Upgrade | The fixture of the last release exists and opens with the current code; the nightly upgrade run passed on a host with jails, a volume, a policy and an exposure | `go test ./internal/upgradecheck`, `scripts/ci-freebsd-upgrade.sh`; `just release-pr` refuses while the newest tag has no fixture |
| Workflows | No row of the daily-task table is MISSING without a reference, and every OK row ran on a host | `scripts/check-workflows-table.sh`, `just e2e-workflows` ([release-engineering.md](release-engineering.md)) |
| Releases | The newest supported FreeBSD release passed the PF traffic matrix and the clean-install run | `scripts/ci-freebsd-pf.sh`, `scripts/ci-freebsd-e2e.sh` on a VM, one run at a time ([testing-on-freebsd.md](testing-on-freebsd.md)) |
| Packages | The packages of the release are on `pkg.jailops.net` for every ABI of the matrix and install and upgrade on a clean host | `just publish-packages`, `pkg update -f -r jailops` on a host |
| Audits | The findings of the last security, lifecycle and architecture audits are fixed or have a written reason | The verdict files of the audits |
| Documents | Roadmap, design and this page say what the code does; no page promises what is not built | The doc invariant tests, a read of [roadmap.md](roadmap.md) and the status register in [design.md](design.md#16-status-register-what-was-assumed-and-what-is-settled) |
